# 舞蹈影片對比

跟著 KPOP 影片練舞之後,把自己的錄影和參考影片並排比對的工具。
純前端,影片不上傳、不離開瀏覽器。

這是「KPOP 舞蹈動作比對」的第一階段 —— 先把影片對比與標註做扎實,
第二階段才接 MediaPipe 姿態偵測與 DTW 動作比對。

## 功能

- **手機優先**:直式 9:16 預設輸出、捏合縮放與拖曳定位、可收合的分頁式面板
- **四種對比模式**:左右、上下、疊加(含差異模式)、可拖曳分割線
- **三種輸出比例**:9:16 / 1:1 / 16:9,並會偵測黑邊過多時主動建議更合適的比例
- **左右鏡像**:可單獨翻轉其中一支。KPOP 的 dance practice 常有鏡像版、
  對著鏡子自拍也會左右相反,不翻過來兩邊動作永遠對不上
- **音訊自動對齊**:兩段影片跳同一首歌時,自動算出時間偏移。
  對不準時直接在時間軸上拖那支影片的色條微調,面板裡另有逐格按鈕
- **逐幀控制**:0.25x–1.00x 無段調速(0.05 一階),`←` `→` 逐幀步進。
  影格率在載入時用 `requestVideoFrameCallback` 實測(不是假設 30),
  匯出時再用容器裡的封包時間戳校正一次 —— 後者更可靠,而且在沒有 rVFC 的
  瀏覽器上是唯一量得到的路徑。兩者都只在使用者沒手動指定時才寫入。
  兩支格率不同時步長取**最細**的那一格 —— 逐格比對時「停在同一張」無所謂,
  「跳過一張」可能就錯過要看的那個瞬間
- **預備拍**:開頭加一段節拍器,並自動偵測歌曲 BPM。
  最後一聲 click 會落在第一個重拍的前一拍,接進去是連續的
- **剪輯**:在播放頭切一刀,選一邊刪掉。可連續切,能復原。
  三分鐘的錄影裡舞常常只有 30 秒,前面是走位、後面是走回去關相機。
  桌機版直接放在時間軸正上方 —— 切點是看著時間軸決定的,按鈕不該在半個畫面外
- **裁切畫面**:框出要留的部分,其餘捨棄,留下的放大填滿該格。
  四角與四邊各自獨立,想只切掉上方的天花板就只拉上邊。
  裁切存的是**原片座標**,所以換輸出比例、換對比模式、平移縮放都不會讓它跑掉
- **時間點文字標註**:指定出現時間與持續長度,文字可直接拖到畫面上任意位置
- **匯出**:WebCodecs 離線編碼,影格直接從檔案解碼,**不必即時播放** ——
  三分鐘的影片不用等三分鐘,也不受「切到其他 App 就錄到空白」的限制。
  輸出 MP4 或 WebM(視瀏覽器支援),編不出來時自動退回 MediaRecorder 即時錄製。
  另有純音訊輸出(WAV)

### 七個值得一提的設計決定

**1. 預覽走 CSS,匯出走 Canvas,但幾何只有一份**

預覽用 CSS `transform` 效能最好,匯出必須用 canvas 才錄得到。
兩套渲染實作最容易出的問題就是「預覽看起來對、匯出卻跑掉」。

解法是把所有版面計算集中在 `lib/layout.ts`,兩邊都只從那裡取數字,
而且 canvas 的操作順序刻意對應 CSS 屬性:

| CSS(預覽) | Canvas(匯出) |
| --- | --- |
| `object-fit: contain` | `containSize()` |
| `transform: translate → scale` | `ctx.translate → scale` |
| `opacity` | `globalAlpha` |
| `mix-blend-mode: difference` | `globalCompositeOperation` |
| `clip-path: inset()` | `ctx.clip()` |
| `scale(-s, s)`(鏡像) | `ctx.scale(-s, s)` |
| 三層盒子 + `overflow: hidden`(裁切) | `drawImage()` 的九參數版本 |

這個等價關係有測試直接驗證:用一個會錄下所有呼叫的假 canvas context 跑 `drawClip()`,
再把 `cssTransform()` 的字串解析出來,逐項比對位移、旋轉、縮放與操作順序。

鏡像刻意排在 `translate` 之後(也就是最先作用在影像上),翻的是影片內容而不是整個版面 ——
位移不會跟著左右顛倒,翻轉前擺好的位置不會跑掉。

裁切是這條規則後來最好的驗證。CSS 沒有 `drawImage()` 的九參數版本,
所以預覽改用三層盒子(格子 → 裁切視窗 → 放大的影片),跟 canvas 那邊長得完全不像;
但兩邊的數字都來自同一支 `cropFrame()` / `containSize()`,所以結果一致。
「留下的部分放大填滿」也不需要另外算放大係數 —— 只要讓 `containSize()` contain
**裁切後**的尺寸,倍率自己就對了。

實作時仍然踩到一個只有真瀏覽器抓得到的坑:Tailwind preflight 有
`img, video { max-width: 100% }`,而裁切時影片寬度要放大到 `1/crop` 倍,
結果**寬度被夾回去、高度卻照放** —— 匯出正確、預覽錯,而且只有橫向錯。
jsdom 沒有排版引擎,量不出這種東西。

**2. 輸出的時間軸由素材決定,不是先選一個格率**

這是花最久才想通的一個。症狀是使用者回報的一句話:**「匯出之後其中一個影片會卡頓」**。

第一版的匯出是先選一個輸出格率,再把兩支素材重新取樣到那個網格上。
問題是格率不同時,網格只能遷就其中一支:30fps 的輸出配 25fps 的素材,
那一支每秒就有 5 張要重複 —— 看起來就是只有它在頓。
而「手機拍的 30fps」配「網路上抓的 24 或 25fps」正是這個 App 最常見的組合。

繞不過去的地方在於**沒有一個格率能同時服務兩邊**:24 與 30 的最小公倍數是 120,
高到不能當輸出格率。前幾輪一直在這個框架裡找補償方案,全部無效,
因為問題不在補償得夠不夠好,而在框架本身。

現在反過來:**先看兩支素材各自的影格落在哪些時刻,再由它們決定要合成幾格。**
合成的時刻是兩支影格時刻的聯集,每一張來源影格都在自己原本的時間點出現剛好一次,
顯示到下一次有畫面要換為止。輸出因此是可變格率(VFR),
而 MP4/WebM 本來就支援,播放器照 PTS 播 —— 「輸出格率」這個概念根本不需要存在。

順帶解掉的是 VFR 素材(手機錄影很常見):它不規則的影格間隔會被原樣保留,
而不是被量化到網格上。舊架構下這是另一個要單獨處理的難題。

唯一要加的一條規則是「差在四分之一格以內就併成同一刻」:
兩支都是 30fps 但對齊偏移 5ms 時,聯集會產生 60 個時刻 —— 格數翻倍、編碼時間翻倍,
但畫面完全沒變好,因為那 5ms 是固定的相位差,不是節奏不對。

驗證方式是做一支每格顏色都不同的測試影片,匯出後把檔案解碼回來逐格比對:

| | 來源張數 | 實際出現 | 重複 | 跳格 |
| --- | --- | --- | --- | --- |
| A(30fps) | 60 | 60 | 0 | 0 |
| B(24fps) | 48 | 48 | 0 | 0 |

影格間隔只有 8.33 / 16.67 / 25 / 33.33 / 41.67ms —— 全是 1/120 秒的整數倍,
正好是 30 與 24 的聯集網格。同一組素材在舊版是 B 每秒重複 6 張。

**3. 同步靠微調速度,不靠 seek**

第一版是牆鐘推進主時鐘,兩支影片誤差超過 60ms 就 `currentTime =` 校正回去。
結果**校正機制本身就是卡頓的來源**:

`video.currentTime` 只在影格邊界更新,30fps 的影片以 ~33ms 為階梯跳動,
所以即使完全同步,量到的誤差也會自然震盪 ±33ms。加上 rAF 抖動就會越過 60ms 門檻,
而播放中 seek 會讓解碼器停頓 → 停頓讓誤差更大 → 於是再 seek。自我強化的迴圈。

現在的做法:

| | |
| --- | --- |
| 主控影片 | 直接拿它的 `currentTime` 當專案時間,它自己播自己的,永遠不校正 |
| 另一支 | 微調 `playbackRate` 慢慢追,靜音時最多 ±10%、有聲音時 ±3% |
| 死區 | 誤差一格以內完全不修正 —— 量化雜訊不該引發反應 |
| seek | 只在誤差 > 250ms(六倍於量化雜訊)時使用 |

**誰當主控**是後來才想清楚的一件事。原本無條件優先 A,結果 720p 配 1080p 時,
被反覆 seek 的永遠是解碼最吃力的那一支 —— 而 seek 就是清空解碼器重來,
慢了誤差更大、於是再 seek。現在改成挑**像素最多的那一支**當主控:
它從此不會被打斷,由便宜的那支去追。代價是有聲音的那支可能變成從屬,
修正幅度只剩 ±3%;用畫面的頓換 3% 的速度變化是划算的,頓看得出來,3% 聽不出來。

死區是關鍵:有了它才敢把增益調高到 2.0,0.24 秒的誤差 2.3 秒收斂完;
沒有死區只能用 0.5,同樣的誤差要拖 7.8 秒,不同步早就被看到了。
這是串流播放器對付時鐘漂移的標準做法。

**4. 剪輯是專案層級的,而且介面是「切開再刪掉」**

這個功能改過兩次,兩次都是被實際使用打回來的。

**第一版:每支影片各自設 in/out。** 它和「對齊」互相打架 ——
裁掉 A 的頭之後,為了不破壞已經對好的同步,必須把 A 在時間軸上往後推同樣的時間。
於是前面多出一段 A 只剩靜止畫格的死區,而且專案總長度根本沒變,**裁了等於沒裁**。
連帶還讓自動對齊的公式多出一項(`offsetB - offsetA = lag + inB - inA`)。

**第二版:專案層級的 in/out。** 資料模型對了 —— 剪輯完全不碰 `offsetMs`(有測試守著),
所以對齊公式退回最單純的 `offsetB - offsetA = lag`。但介面還是難用:
「起點設為現在 / 訖點設為現在」是編輯器的說法,
使用者得先在腦中把要保留的範圍想清楚,才知道該按哪一個。

**現在:切開,然後刪掉不要的那半。** 底層資料完全沒變 ——
在 T 切開刪左邊就是 `rangeIn = T`,刪右邊就是 `rangeOut = T` ——
但不用先想清楚,看著畫面做就好。連續切兩刀就能同時去頭去尾。

刪掉的部分在時間軸上壓暗但仍然看得到,可以復原,也可以還原成完整長度。
播放只在保留的區間內跑,所以預覽看到的就是匯出會拿到的東西。

桌機版把這組操作攤平放在**時間軸正上方**,而不是右側面板裡:
切點是盯著時間軸決定的,「切開 → 刪哪一邊」是緊接著的第二步,
隔著半個畫面來回看,每切一刀都要重新找一次按鈕。手機沒有這個橫向空間,
維持分頁裡的面板 —— 兩套版面共用 `useTrim()`,規則不會有一天開始不一樣。

> 目前只支援單一連續區間,不能挖掉中間再接起來。
> 對「去頭去尾」這個實際需求夠用。
> (換成 WebCodecs 之後接縫本身已經不是問題 —— 合成時間軸是自己排的,
> 要跳過中間一段只是不產生那些時刻;卡住的是介面,多段區間的拖拉與復原
> 遠比「切一刀選一邊」複雜。)

**5. 需要「看著調」的東西,一律做成直接操作**

這個專案的介面改過三輪,每一輪都是同一個毛病:我做了「輸入一個數字」的控制項,
但使用者要的是「抓著它移」。

| 原本 | 現在 |
| --- | --- |
| 縮放 / 位移 slider | 在畫面上拖曳、兩指捏合、滑鼠滾輪 |
| 設起點 / 設訖點 | 切一刀,刪掉不要的那半 |
| 時間偏移 ±100ms 按鈕 | 在時間軸上直接拖那支影片的色條 |

判準是:**這件事需不需要看著結果才知道對不對?** 需要的話就不能用數字輸入。
反過來,拖不出來的精度才留按鈕 —— 逐格步進、逐格偏移、±10% 縮放。

但改成直接操作有個容易漏的坑:**手勢不是每種輸入裝置都做得到**。
捏合縮放需要兩個指標,滑鼠只有一個 —— 桌機因此一度完全無法縮放。
所以每個直接操作都要配一條非手勢的路:滾輪、或面板上的按鈕。

滾輪縮放以**游標為錨點**而不是格子中心(`lib/zoom.ts`)。
繞著中心縮放的話,放大時你盯著的那個點會往外飄走,每放大一次都要重新拖回來找目標。
測試用的是「來回縮放後位移必須回到原點」—— 錨點算錯就會留下殘餘偏移。

時間軸因此分成兩區:上方刻度尺拖播放頭,下方色條拖影片。
拖曳期間會凍結時間軸的顯示長度,否則色條往右移、專案變長、整條軸跟著縮,
手指和色條會對不上。

**6. 播放時間不放在 store 裡**

播放時這個值每幀都變,放進 zustand 等於每秒觸發 60 次 React reconciliation,
跟影片解碼搶 main thread。改成兩層:`playbackClock` 每幀更新給 rAF 迴圈直接讀,
store 只保留 10Hz 的節流鏡像給需要重新渲染的東西(標註的出現與消失)。
逐幀步進與新增標註都讀時鐘,否則會差到三格。

**7. 舞台不用 JavaScript 量任何東西**

原本是 `ResizeObserver` 量出縮放倍率再套 `transform: scale()`。
手機上旋轉螢幕、網址列收合、鍵盤彈出都會改變可用高度,
只要有一次通知沒送到,整個預覽就停在錯的比例 —— 而且很難重現。

改成方框用 container query 單位做 contain-fit、內部一律用百分比(字級用 `cqw`):

```css
width: min(100cqw, calc(100cqh * 1080 / 1920));
```

`layout.ts` 仍然是唯一的幾何來源,只是在寫進 CSS 前換算成相對單位 ——
`cssTransform()` 輸出 `translate(50%)` 而不是 `translate(270px)`,
因為套用它的那一層**就是一整格大小**,`offsetX / slot.w × slot.w` 恰好等於
canvas 用的 `offsetX`。這條等價關係有測試守著。

做裁切時差點踩壞它:裁切要在影片外面再包一層「裁切視窗」,而那一層比格子小,
transform 掛上去的話百分比的基準就變了,位移會跟著縮水。
所以 transform 留在整格大小的外層,裁切視窗放在它裡面 ——
縮放的原點也因此仍然是格子中心,與 `drawClip()` 一致。

## 音訊自動對齊怎麼做的

兩段影片配的是同一首歌,音訊內容幾乎相同、只差一個時間偏移。

```
解碼 → 混單聲道 → 100Hz 音量包絡 → 對數壓縮 → 正向差分(起音強度)
     → z-score 正規化 → FFT 互相關 → 重疊區 Pearson 相關係數 → 找峰值
```

**為什麼比對「起音強度」而不是音量包絡**
音量包絡會被兩支影片的錄音音量、EQ、環境噪音整體平移。
正向差分只留下音量突然變大的瞬間,也就是鼓點和重拍,對響度差異免疫,峰值也尖銳得多。

**為什麼用 FFT**
兩段 3 分鐘的 100Hz 包絡各 18000 點,直接算互相關是 O(n²) 約 3.24 億次乘法;
走 FFT 是 O(n log n),約 65 萬次。實測 3 分鐘音訊在 100ms 內算完(有單元測試守著)。

### 找不到可信度指標這件事

偏移量本身算得很準,但「這次到底對了沒有」意外地難判斷。試過三種指標,全部失敗:

| 情境 | 相關係數 | z-score | margin |
| --- | --- | --- | --- |
| 完全相同 | 1.000 | 7.4 | 0.076 |
| 音量差 3 倍 + 雜訊 | 0.914 | 7.4 | 0.074 |
| 重雜訊(仍對齊成功) | 0.656 | 7.3 | 0.061 |
| 雜訊蓋過訊號 | 0.301 | 7.2 | 0.030 |
| **兩首無關的歌** | **0.927** | **6.8** | **0.003** |
| **純節拍器(對錯小節)** | **1.000** | **7.0** | **0.000** |

1. **z-score(峰值對全體分數)** —— 不管對不對都落在 7.0~7.4,毫無鑑別力。
2. **相關係數本身** —— 兩首無關但同 BPM 的歌照樣拿 0.93,因為拍點位置本來就對得上;
   節奏重複的舞曲對到隔壁小節更是直接滿分。
3. **margin(主峰比次高峰高多少)** —— 上表看起來能分開,但換一種素材就破功:
   純打擊樂(嗶聲 + 靜音)的正確答案 margin 只有 0.006,和退化情況幾乎重疊。
   任何固定門檻都會誤報。

**結論:沒有便宜的純量能判斷成敗。** 與其給一個假裝有把握的分數,
不如把分數接近的第二個位置一起交出來,讓使用者一鍵切換、用波形自己確認 ——
時間軸上的兩條波形本來就是最直接的驗證工具。

這也是為什麼波形跟自動對齊共用同一份包絡:分析一次,對齊和視覺化都吃它。

## BPM 偵測與預備拍

測速完全重用對齊已經算好的那份起音包絡 —— 那本來就是「鼓點落在哪」的序列,
連 FFT 都不用再寫一份:**自相關就是訊號和自己做互相關**。

```
onset 包絡 → 自相關 → 諧波加總 → 速度先驗加權 → 拋物線內插 → BPM
                                                 → 脈衝串掃描 → 相位
```

### 三個必要的細節

**平滑化,否則高速會被判成一半。**
100Hz 的包絡在 160 BPM 時一拍是 37.5 格 —— 真正的週期落在格點之間,
基頻的自相關峰值被量化抹平,而 2 倍週期(75 格,剛好整數)反而更銳利,
結果 160 會被判成 80。先把起音抹開約 ±20ms,再用 0.25 格的分數延遲搜尋才解得掉。

**速度先驗處理八度誤判。**
自相關在 55、110、220 BPM 都有同樣高的峰值。硬性折疊到某個區間會把真正的慢歌
誤判成兩倍速,所以改用以 120 BPM 為中心、寬 0.7 個八度的高斯權重 ——
靠近 120 的候選有優勢,但夠強的慢速峰值仍然贏得了。

**相位決定這功能有沒有用。**
只知道 110 BPM 不夠,還要知道拍點落在哪。設前綴長度 P、一拍 T、
歌曲第一個重拍在內容時間 φ,則預備拍第 k 聲要落在 `P + φ − kT`,
取 `P = 拍數 × T − φ` 讓開頭不留空白。這樣最後一聲剛好在第一個重拍的前一拍。
不管相位的話節拍器會跟歌整個錯開,加了等於沒加。

### 信心度又踩了同一個坑

第一版的信心度是「主峰領先次高峰的幅度」,結果**均勻白雜訊拿到 0.82**,
跟乾淨的拍子一樣高 —— 雜訊的所有分數都趨近 0,隨機的最大值除以次大值
照樣得到漂亮的比例。**比值型指標在分母很小時會爆掉**,
這跟音訊對齊那邊踩過的是同一個坑。

補上一個絕對量(偵測到的週期上的正規化自相關值)之後就分開了:

| | strength | margin | conf |
| --- | --- | --- | --- |
| 乾淨 128 BPM | 0.916 | 0.801 | 0.801 |
| 重雜訊(仍正確) | 0.172 | 0.683 | 0.172 |
| 雜訊蓋過訊號(錯誤) | 0.065 | 0.315 | 0.065 |
| **均勻白雜訊** | **0.080** | **0.820** | **0.080** |

`confidence = min(strength, margin)`,門檻 0.12。
偵測正確 0.17~0.84,失敗 0.02~0.08,中間有空隙。

### 節拍器的聲音

用 Web Audio 的 `osc.start(when)` 一次排完所有 click,不用 rAF 觸發 ——
rAF 的時間點會抖 ±16ms,預備拍抖成那樣就失去意義了。

匯出時影片音源與 click 混進同一個 `MediaStreamDestination`。
全部走 Web Audio 而不是 `video.captureStream()`,因為 Safari 根本沒實作後者,
不處理的話 iPhone 匯出會靜音 —— 而手機正是主要使用場景。

### 驗證到什麼程度

- `npm test` 涵蓋互相關的正負號、雜訊與音量差的容忍度、退化情況的偵測、效能上限、
  播放同步的時間換算(offset 方向弄反的話畫面照樣會動,很難用眼睛發現),
  以及漂移校正的收斂行為(死區蓋得住量化雜訊、修正單向不震盪、最差情況 3 秒內收斂)。
- 端到端跑過一次真實路徑:在瀏覽器合成兩支 WebM(同一段節拍,B 晚 2.37 秒開始),
  走完 `decodeAudioData` → 包絡 → 對齊,結果是 **2.37s、相關係數 1.00、耗時 16ms**。
- BPM 偵測同樣端到端驗過:合成 128 BPM 的真實音訊(鼓點從第 200ms 開始),
  測得 **127.8 BPM、信心度 0.80、耗時 19ms**;
  8 拍預備拍算出 3.57s 而不是 3.756s,差的 186ms 正是偵測到的相位 —— 相位確實抓到了。
- **播放與匯出尚未實測** —— 需要實際開瀏覽器操作。
  節拍器的聲音尤其如此:它整個活在音訊路徑上,而那是這個環境唯一驗證不了的部分。

## 手機上的取捨

- **輸出比例會影響黑邊,而且不直覺。** 兩支手機直拍的影片左右並排時,
  填充率最高的是 **方形** 輸出(88.9%),不是直覺的橫式(63.3%)或直式(50%)——
  把正方形對半切得到 1:2 的格子,最接近 9:16 影片。
  所以這個判斷交給 `bestAspect()` 算,不靠感覺。
- **Safari 沒有 `HTMLMediaElement.captureStream()`。** 不處理的話 iPhone 匯出會靜音。
  已改成偵測不到就退回 Web Audio(`MediaElementSource → MediaStreamDestination`)。
- **調整畫面要明確開關。** 手勢隨時都能拖曳的話,想捲動頁面會誤觸;
  所以只有按下「用手勢調整畫面」或「裁切畫面」時才設 `touch-action: none`。
  兩個模式也互斥 —— 它們都要吃舞台上的指標事件,同時開著會互相搶。
- **輸入框字級不能小於 16px。** iOS Safari 會因此自動放大整個頁面,
  所以 `inputClass` 在小螢幕用 `text-base`,桌機才降回 `text-xs`。
- **編碼器不進首屏。** mediabunny(解封裝 + 封裝)minify 後 648KB,
  佔整包八成以上,但只有匯出才用得到。全部靜態 import 的話首屏是 212KB(gzip),
  改成動態載入之後剩 87KB:

  | 何時載入 | gzip |
  | --- | --- |
  | 首屏(UI + 播放引擎) | 87KB |
  | 載入素材後(偵測編碼能力) | +22KB |
  | 按下匯出(解封裝 + 封裝) | +107KB |

  代價是冷啟動時按下匯出會多等一段下載,所以那段按鈕會顯示「準備編碼器…」。
  `outputFormatFor()` 也因此從 `capabilities.ts` 搬到 `videoExport.ts` ——
  封裝器很大,不該被「只是看一眼編碼能力」拖進來。

## 記憶體:為什麼分析用 16kHz 解碼

`decodeAudioData` 會把音訊重新取樣到 context 的取樣率,所以那個數字直接決定
解碼後佔多少記憶體:

| 3 分鐘的影片 | 每支 |
| --- | --- |
| 48kHz 立體聲 | 約 69 MB |
| 16kHz 單聲道 | 約 11.5 MB |

兩支就是 138MB 對 23MB。在 iPhone 上前者很容易讓 Safari 直接把分頁回收掉 ——
症狀就是「從相簿選完影片後回不到網頁」。

沒有壓到 8kHz 是因為包絡是靠每 10ms 的 RMS 能量算的,取樣率太低會濾掉小鼓與
hi-hat 的高頻瞬態,起音會變鈍。16kHz 保留到 8kHz,鼓組的資訊幾乎都還在,
而包絡本身只有 100Hz,遠遠夠用。

同樣為了 iOS,檔案選擇改成 `<label htmlFor>` + `sr-only` 的 input,
不再用 `display:none` 加 JS `.click()` —— 那個組合在 iPhone 上會出現
「按打勾沒反應」。

## 已知限制

- **匯出很吃記憶體**:一次 3 分鐘 1080p 的峰值包含兩支完整檔案的 Blob、
  兩份 44.1kHz 立體聲 PCM(各約 63MB)與混音輸出,加上 `CanvasSink` 目前
  每一格都配一張全解析度 canvas(1080p = 8.3MB/張)。手機上這是最可能爆掉的地方,
  而一旦 WebCodecs 匯出失敗就會退回即時錄製 —— 那條路會把預覽的卡頓錄進檔案。
  要修的是分塊解碼音訊,以及給 `CanvasSink` 設 `poolSize`
  (但池子太小會在畫面還在用的時候被回收,大小要算清楚,不能隨手填)。
- **輸出是可變格率**:這是設計決定 2 的必然結果,也是兩支素材都不頓的前提。
  瀏覽器與一般播放器都沒問題,但少數剪輯軟體偏好固定格率的素材。
- **輸出容器看瀏覽器**:優先用 MP4/H.264(唯一 iPhone、Android、桌機全都播得了的組合),
  編不出來時退回 WebM —— 那個 iPhone 打不開,所以介面會事先警告。
- **`decodeAudioData` 吃整段音訊**:很長的影片會佔記憶體,手機上尤其明顯,
  之後要改成分塊解碼。(對齊分析那條已經用 16kHz 單聲道解掉了,見下。)
- **重整就全沒了**:目前沒有任何持久化,兩支影片、對齊偏移、裁切、剪輯範圍、
  標註都存在記憶體裡。對齊加裁切花好幾分鐘,誤觸重整就要重來。
- **同時解兩支高解析度影片**:手機上很吃力,預覽會頓(匯出不受影響,那是離線解碼)。
  偵測到反覆硬 seek 時會停止校正並在介面說明原因,而不是讓人以為網站壞了。
- **元件層沒有測試**:邏輯層蓋得很滿(222 個測試),但 UI 只有手動驗證。
  而且像上面那個 `max-width` 的坑,jsdom 沒有排版引擎、本來就抓不到,
  要蓋只能上真瀏覽器的 smoke test。
